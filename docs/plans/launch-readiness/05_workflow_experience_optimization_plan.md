# 05 工作流用户体验优化专项计划

## 0. 目标

工作流不是给用户展示“我们有 DAG 和节点编排能力”，而是让营销团队把一套可复用的生产 SOP 保存下来，并能稳定运行、排错、复用和交接。

上线测试前的目标：

1. 非技术运营能理解每个节点在业务上做什么。
2. 用户运行前知道这条工作流是否能跑、预计花多久、可能消耗多少。
3. 运行中能看懂当前卡在哪个步骤，而不是只看到整体 loading。
4. 失败后能只重试失败节点，或从某个节点继续向后跑。
5. 成功工作流能沉淀成团队模板，而不是一次性草稿。
6. 工作流产物能进入资产库和审阅链路。

## 1. 当前状态

现有能力：

- 前端已有 React Flow 工作流画布：`frontend/src/components/WorkflowBuilder.tsx`。
- 节点类型、默认节点、I/O schema 已集中在 `frontend/src/features/workflows/constants.ts`。
- 右侧属性面板已有运行预览、节点进度、基础检查：`PropertyPanel.tsx`。
- 支持草稿保存、加载、自动布局、撤销/重做、复制/粘贴、只读分享。
- 支持节点配置弹层、失败节点重试、自定义智能体。
- 后端已有 `WorkspaceDraft` 和 `WorkflowTemplate`，并支持模板 fork。
- 后端运行逻辑已有拓扑排序、schema 校验、节点运行和重试入口。

当前主要问题：

- 节点命名仍偏工程化，例如“文案节点”“检索节点”“图片提示词”。
- 运行前检查只是提示数量，缺少强阻断和具体修复动作。
- 工作流模板缺少“适用场景、预计产物、所需输入、预计耗时、风险提示”。
- 节点失败后的恢复路径不够产品化，用户不知道该重试、改输入、换模型还是跳过。
- 运行结果与资产库、审阅、模板复用之间的闭环还不够明确。
- 自定义智能体对普通用户仍偏高级，没有足够安全边界。

## 2. 用户旅程

### 2.1 首次进入工作流

用户应该看到：

- 当前项目和活动。
- 这条工作流将产出什么。
- 当前品牌记忆是否足够。
- 推荐从哪个模板开始。
- 一个明显的主按钮：运行工作流。

不应该一上来要求用户理解：

- DAG。
- input_schema / output_schema。
- 节点坐标。
- 上游/下游数据结构。

### 2.2 创建或编辑工作流

用户的自然语言任务是：

- 读取品牌信息。
- 查找历史素材。
- 写渠道文案。
- 生成图片建议。
- 生成配图。
- 生成分镜。
- 合成配音。
- 生成视频。
- 审核合规。

工程概念只能在高级配置里出现。

### 2.3 运行工作流

运行前用户要知道：

- 是否缺少品牌记忆。
- 是否有断开的节点。
- 是否有必要字段没填。
- 哪些节点会调用模型。
- 预计耗时。
- 预计额度或成本。
- 失败后是否会自动重试。

运行中用户要知道：

- 当前正在执行哪个业务步骤。
- 已完成哪些产物。
- 失败节点的原因和恢复动作。
- 能不能安全离开页面。

运行后用户要知道：

- 生成了哪些资产。
- 哪些内容需要审阅。
- 哪些节点可以再次运行。
- 是否可以保存为模板。

## 3. 信息架构升级

### 3.1 节点业务化命名

| 当前节点 | 用户看到的名称 | 用户解释 |
| --- | --- | --- |
| Context | 读取品牌记忆 | 使用当前项目的品牌、受众、语调和禁区 |
| Retrieval / RAG Search | 查找历史素材 | 从资产库和授权资料里找可复用素材 |
| Copy | 写渠道文案 | 按渠道规则生成标题、正文、标签和 CTA |
| Image Prompt | 生成图片说明 | 把文案转成可用于生图的视觉描述 |
| Image Generation | 生成配图 | 调用图片模型生成可保存的视觉资产 |
| Storyboard | 生成分镜脚本 | 把主题拆成镜头、旁白和时长 |
| Audio | 合成配音 | 将口播文本转成音频资产 |
| Video Generation | 生成视频 | 根据提示词、分镜或参考图生成视频 |
| Review | 内容审阅 | 检查禁用词、品牌一致性和渠道规则 |
| Custom Agent | 自定义步骤 | 高级用户定义自己的输入、提示词和输出 |

实施要求：

- `nodeTypeLabels` 和 `presets` 使用业务名称。
- 画布节点标题显示业务名称。
- schema 字段放到“高级配置”折叠区。
- 节点详情中增加“一句话说明”和“预计产物”。

### 3.2 模板信息结构

每个工作流模板必须有：

- 模板名称。
- 适用场景。
- 需要输入。
- 预计产物。
- 推荐渠道。
- 预计耗时区间。
- 预计消耗等级：低 / 中 / 高。
- 风险提示：例如视频节点耗时长、公开发布前必须审阅。

模板示例：

| 模板 | 适用场景 | 预计产物 |
| --- | --- | --- |
| 小红书新品种草 | 新品上市首波内容 | 标题、正文、标签、配图提示、合规检查 |
| 短视频脚本生产 | 抖音/视频号脚本 | 分镜、口播、配音建议、视频提示词 |
| 公众号长文复用 | 将已有 brief 扩展成长文 | 标题、导语、正文结构、配图建议 |
| 竞品素材复盘 | 团队资料和公开素材整理 | 参考摘要、洞察、可复用角度 |

## 4. 运行前检查

### 4.1 检查项

运行前检查分为三类。

阻断项：

- 没有节点。
- 必要节点断开。
- 存在循环。
- 必填字段为空。
- 当前用户没有运行权限。
- 当前项目不存在或没有活动上下文。

强提醒项：

- 品牌记忆完整度低于 50。
- 没有审阅节点。
- 视频节点存在但没有参考图或明确 prompt。
- 图片生成节点没有负面提示词。
- 自定义智能体没有输出 schema。

信息项：

- 节点数量。
- 会调用模型的节点数量。
- 预计耗时。
- 预计消耗等级。
- 预计会生成的资产类型。

### 4.2 UI 形态

运行按钮点击后先打开“运行前检查”面板，而不是直接执行。

面板内容：

- 顶部结论：可以运行 / 建议修复后运行 / 当前不能运行。
- 检查列表：每项有状态、原因、修复按钮。
- 成本和耗时估算。
- 本次使用的品牌记忆摘要。
- 主按钮：确认运行。

修复按钮示例：

- “补齐品牌记忆”跳转项目检查器。
- “定位断开节点”选中节点并高亮连线区域。
- “填写配置”打开节点配置弹层。
- “添加审阅节点”自动添加 Review 节点并连线。

### 4.3 验收标准

- 有阻断项时不能执行工作流。
- 每个阻断项都必须有明确修复动作。
- 用户不需要看 console 或 raw error 就能知道为什么不能运行。
- 检查面板在 375px 宽度可操作。

## 5. 运行中体验

### 5.1 节点级状态

每个节点状态必须清晰：

- 未开始。
- 等待上游。
- 排队中。
- 运行中。
- 保存资产中。
- 成功。
- 失败。
- 已跳过。

运行中需要显示：

- 当前节点业务名称。
- 当前节点在第几步。
- 已完成 / 总节点数。
- 当前节点已耗时。
- 长任务提示，例如视频节点可能需要数分钟。

### 5.2 输出预览

节点成功后，用户应该立刻看到简短产物摘要：

- 文案：标题、正文摘要、标签数量。
- 图片提示词：prompt 摘要、比例、风格。
- 图片：缩略图、保存状态。
- 分镜：镜头数量、总时长。
- 配音：音频时长、声线。
- 视频：缩略图、视频时长、处理状态。
- 审阅：风险数量、是否通过。

### 5.3 离开页面提示

长任务运行时：

- 告诉用户可以离开，任务中心会继续跟踪。
- 页面刷新后能恢复最近运行状态。
- 右侧任务中心能显示工作流任务。

### 5.4 验收标准

- 用户能在 5 秒内判断当前卡在哪个节点。
- 视频节点运行超过 30 秒时必须显示长任务提示。
- 刷新页面后能看到最近一次运行结果或运行状态。
- 节点输出摘要不展示 raw JSON，除非进入高级详情。

## 6. 失败恢复

### 6.1 失败原因分级

| 失败类型 | 用户文案 | 推荐动作 |
| --- | --- | --- |
| 输入缺失 | 这个步骤缺少必要输入 | 打开配置并补齐 |
| 上游输出不匹配 | 上一步产物不能被当前步骤使用 | 查看上游输出 / 调整连线 |
| 模型超时 | 模型响应超时，可能是输入过长或服务繁忙 | 缩短输入 / 重试 / 换模型 |
| 额度不足 | 当前额度不足，无法继续运行 | 查看计费 / 联系管理员 |
| 权限不足 | 你没有运行或编辑这条工作流的权限 | 切换项目 / 联系管理员 |
| 合规拦截 | 内容触发了品牌或平台限制 | 查看审阅建议 / 修改输入 |
| 资产保存失败 | 内容生成成功，但保存到资产库失败 | 重试保存 / 下载临时结果 |

### 6.2 恢复动作

必须支持：

- 重试失败节点。
- 从当前节点向后重跑。
- 复制失败节点输入。
- 查看上游输入和当前输出。
- 跳过非关键节点继续运行。

后续增强：

- 换模型后重试。
- 降低质量档位后重试。
- 对失败节点生成“修复建议”。

### 6.3 验收标准

- 失败后不能只显示后端原始错误。
- 用户能只重试失败节点，不需要重跑全链路。
- 重试要使用 idempotency key，避免重复扣费。
- 节点失败和任务失败在 UI 上能对应起来。

## 7. 产物闭环

### 7.1 自动入资产

工作流运行成功后，节点产物应进入资产库：

- Copy -> document asset。
- Image Prompt -> prompt/document asset。
- Image Generation -> image asset。
- Storyboard -> document asset。
- Audio -> audio asset。
- Video -> video asset。
- Review -> review record 或 document asset。

资产 metadata 应包含：

- workflow_draft_id。
- workflow_run_id。
- node_id。
- node_type。
- generation_task_id。
- project_id。
- campaign_id。
- model/provider。
- cost/token。

### 7.2 审阅闭环

如果存在 Review 节点：

- 审阅通过的资产标记为可发布。
- 审阅失败的资产进入待修改。
- 风险项应能回链到产生该内容的节点。

如果没有 Review 节点：

- 运行后提示“建议送审后再发布”。
- 支持一键添加 Review 节点。

### 7.3 验收标准

- 用户在资产库能按工作流、节点、项目找到产物。
- 成功运行的工作流不会只留在画布里。
- 审阅风险可追溯到具体节点。

## 8. 模板化复用

### 8.1 保存为模板

成功运行后展示“保存为模板”：

- 模板名称默认来自项目 + 产物类型。
- 自动生成适用场景。
- 自动生成预计产物。
- 自动剥离本项目敏感品牌数据。
- 用户确认可见范围：仅自己 / 工作区 / 公开。

### 8.2 模板库边界

上线测试期默认：

- 工作区模板只对当前组织可见。
- 公开模板必须二次确认。
- 公开模板不得包含客户名、私有链接、项目 brief 原文。
- Fork 模板后生成新的 WorkspaceDraft，不能污染原模板。

### 8.3 验收标准

- 成功运行后 1 次点击可进入模板保存流程。
- 保存公开模板必须二次确认。
- 公开模板能通过脱敏检查。

## 9. 权限与安全

### 9.1 权限矩阵

| 操作 | Admin | Creator | Ops | Viewer |
| --- | --- | --- | --- | --- |
| 查看工作流 | 是 | 是 | 是 | 是 |
| 编辑节点 | 是 | 是 | 是 | 否 |
| 运行工作流 | 是 | 是 | 是 | 否 |
| 重试节点 | 是 | 是 | 是 | 否 |
| 保存模板 | 是 | 是 | 是 | 否 |
| 发布公开模板 | 是 | 需确认/可配置 | 否 | 否 |
| 配置模型/密钥 | 是 | 否 | 否 | 否 |

### 9.2 自定义智能体安全

自定义智能体必须限制：

- 默认只允许工作区内使用。
- 输出 schema 必填。
- 明确提示词可见范围。
- 禁止 Viewer 创建或编辑。
- 公开模板保存前必须清理 prompt 中的客户信息和密钥。

### 9.3 验收标准

- Viewer 进入工作流时看到只读模式，不能通过前端按钮触发运行。
- 后端必须再次校验权限，不能只靠前端隐藏按钮。
- 模板公开前有脱敏检查。

## 10. 可访问性与移动端

必须完成：

- 所有 icon button 有 `aria-label` 或明确 title。
- 节点配置弹层支持 Esc 关闭。
- 运行前检查面板支持键盘操作。
- 节点列表可用键盘选择。
- 375px 宽度下至少能完成查看、运行、查看失败原因。
- 长节点名、长错误、长 prompt 不撑破面板。

验收标准：

- Keyboard only 可完成保存、运行、查看失败原因。
- 移动端不出现不可点击的主按钮。
- 错误信息不遮挡“重试”和“修复”按钮。

## 11. 指标与运营观测

上线测试需要记录：

- 工作流页访问率。
- 模板选择率。
- 首次保存工作流率。
- 首次运行工作流率。
- 运行前检查阻断率。
- 阻断项类型分布。
- 工作流运行成功率。
- 节点失败率，按 node_type 分组。
- 节点重试率。
- 从失败节点恢复成功率。
- 保存为模板率。
- 模板 fork 率。
- 工作流产物进入资产库率。

这些指标不一定第一版全做前端埋点，但后端任务日志至少要能反查。

## 12. 后端架构与性能优化

工作流体验能不能稳定上线，后端比前端更关键。当前 `run_workspace_workflow()` 是同步顺序执行，节点状态直接写回 `WorkspaceDraft.nodes` JSON。这个方案适合 demo，但生产测试会遇到性能、并发、重试、审计和恢复问题。

### 12.1 当前后端风险

现状风险：

- 工作流运行是同步串行流程，长任务会占住请求链路。
- 每个节点状态变化都会保存整个 `draft.nodes` JSON，节点多时写放大明显。
- 节点运行态、草稿配置态、历史运行结果混在同一个 JSON 字段里。
- 缺少独立的 `workflow_run_id`，难以追踪一次运行的完整生命周期。
- 节点重试依赖当前 draft 状态，缺少强 idempotency 约束，存在重复运行和重复扣费风险。
- 无法并行执行同一层级的独立节点。
- 缺少取消、超时、限流、队列积压保护。
- 节点输出没有统一大小限制，大输出会拖慢 draft 序列化。
- 运行进度依赖轮询完整 draft，后续节点多时接口响应会越来越重。

### 12.2 目标后端架构

建议新增运行态模型，将“草稿配置”和“运行实例”拆开。

核心模型：

- `WorkflowRun`
  - draft、organization、project、campaign。
  - status：queued、running、succeeded、failed、cancelled、partial_success。
  - started_at、completed_at。
  - idempotency_key。
  - graph_version。
  - total_nodes、completed_nodes、failed_nodes。
  - estimated_cost、actual_cost、token_count。

- `WorkflowNodeRun`
  - workflow_run。
  - node_id、node_type、node_label。
  - status：pending、queued、running、saving_asset、succeeded、failed、skipped、cancelled。
  - started_at、completed_at、duration_ms。
  - input_snapshot、output_summary、error_code、error_message。
  - generation_task。
  - retry_of、attempt。

- `WorkflowRunEvent`
  - workflow_run。
  - event_type：run_started、node_started、node_succeeded、node_failed、asset_saved、run_completed。
  - node_id。
  - payload。
  - created_at。

保留 `WorkspaceDraft.nodes` 作为编辑态，不再把每次运行的大量 runtime 状态长期混入草稿。

### 12.3 执行引擎优化

执行层建议分两步升级：

第一步：异步化和运行态拆分。

- `/drafts/<id>/run/` 只创建 `WorkflowRun` 并立即返回 run id。
- Celery worker 执行 `WorkflowRun`。
- 前端轮询 `/workflow-runs/<id>/` 或后续接 SSE/WebSocket。
- 每个节点写入 `WorkflowNodeRun`，草稿只在必要时更新摘要。

第二步：图编译和可并行执行。

- 运行前将 nodes/edges 编译成 execution plan。
- 拓扑排序改成分层执行。
- 同层无依赖节点可以并行入队。
- downstream 节点只在所有必要上游成功后执行。
- 节点失败根据 failure_strategy 决定：中断、跳过、走 fallback 分支、只标记失败。

### 12.4 数据库和接口性能

优化方向：

- 给 `WorkflowRun` 增加 `(organization, status, created_at)` 索引。
- 给 `WorkflowNodeRun` 增加 `(workflow_run, status)` 和 `(generation_task)` 索引。
- 工作流列表接口默认不返回完整 nodes/output，只返回摘要。
- draft 详情接口支持 `?include_runtime=false`。
- 节点输出大字段不要反复塞回 draft，资产和输出详情按需加载。
- 对 `last_run_summary` 做小摘要，不保存完整结果。
- 对 workflow template 列表做分页和 visibility 过滤。
- 对频繁读取的品牌记忆摘要做短期缓存或 run input snapshot。

### 12.5 队列、限流和成本保护

必须补齐：

- 按组织、用户、plan 限制并发运行数。
- 视频、图片等高成本节点单独队列或优先级。
- 每次运行前预估成本，超过阈值需要确认。
- 并发节点数有上限，避免一个工作流占满 worker。
- provider 超时要写入可恢复错误码。
- 节点级 idempotency key：`workflow_run_id + node_id + attempt`。
- 取消运行时，未开始节点标记 cancelled，运行中节点尽力取消或标记 cancelling。

### 12.6 可观测性

后端需要支持排障：

- 每个 WorkflowRun 有 trace id。
- 每个节点记录 provider、model、latency、token、cost。
- 错误分类使用稳定 error_code，不只存字符串。
- 保存审计日志：run、retry、cancel、template_publish、visibility_change。
- 管理员能看到队列积压、失败率、平均耗时、成本异常。

### 12.7 验收标准

- 运行接口 P95 响应小于 500ms，因为只创建 run，不同步跑完整工作流。
- 20 节点工作流运行中，轮询接口响应仍小于 300ms。
- 独立分支节点可以并行执行。
- 刷新页面后可通过 run id 恢复完整运行状态。
- 节点重试不会重复扣费。
- 管理员能按 run id 查到完整节点执行链路。

## 13. DAG 扩展：分支、判定和合流

当前 DAG 是线性或普通依赖图。要支持更真实的营销 SOP，需要加入分支结构、判定结构和合流结构，但必须控制复杂度，避免变成低代码平台。

### 13.1 新节点类型

建议新增：

- `decision` / 判定节点
  - 根据上游输出、审阅结果、分数、关键词判断走哪条路径。
  - 示例：如果审阅风险 > 0，进入修改分支；否则进入发布准备。

- `router` / 分流节点
  - 按渠道、受众、内容类型分发到多个分支。
  - 示例：小红书走短文案 + 配图，公众号走长文结构。

- `join` / 合流节点
  - 等待多个分支完成后合并摘要。
  - 示例：汇总文案、图片、审阅结果，生成最终交付包。

- `human_approval` / 人工确认节点
  - 暂停工作流，等待用户批准后继续。
  - 示例：合规高风险内容必须人工确认。

- `fallback` / 兜底节点
  - 当主分支失败或不满足条件时执行。
  - 示例：视频生成失败时保留分镜和图片资产作为交付。

### 13.2 边结构升级

现有 edge 只有 source/target，不足以表达条件。建议扩展：

- `source_handle`：从哪个输出口出发，例如 yes/no/default。
- `target_handle`：进入目标节点的哪个输入口。
- `condition`：条件表达式。
- `condition_label`：给用户看的条件名。
- `is_default`：是否默认路径。
- `priority`：多个条件同时满足时的顺序。

条件表达式第一版不要做任意 JS。建议使用受限表达式：

- 字段选择：`review.risk_count`、`copy.title`、`asset.type`。
- 操作符：等于、不等于、大于、小于、包含、为空、不为空。
- 值：字符串、数字、布尔。
- 组合：AND / OR，最多两层。

后续如需复杂逻辑，可考虑 JSONLogic，但第一版应先做可视化条件构建器。

### 13.3 执行语义

执行规则：

- decision/router 节点本身可以不调用模型，只负责判断。
- 未命中的分支节点标记 skipped。
- join 节点默认等待所有“被激活”的上游分支。
- join 可以配置策略：全部成功、任一成功、允许部分失败。
- 禁止无界循环。
- 如果后续支持循环，必须设置最大迭代次数和成本上限。

### 13.4 前端表达方式

画布上需要：

- 判定节点显示 yes/no/default 输出口。
- 分支连线显示条件标签。
- 被跳过分支用灰色虚线显示。
- 运行中高亮实际走过的路径。
- 用户点击条件边可打开条件编辑器。

运行前检查需要新增：

- 每个 decision 至少有一个默认路径。
- 条件字段必须来自上游可用输出。
- join 不能等待永远不会激活的分支。
- 分支不能形成循环。

### 13.5 验收标准

- 用户能配置“审阅通过则进入发布准备，否则进入修改分支”。
- 运行后能看到实际命中的分支路径。
- 未命中的节点不会被错误执行或扣费。
- 条件配置错误会在运行前被拦截。
- 后端执行结果能记录 branch trace。

## 14. 其他后端优化方向

从生产级角度，还缺以下方向。

### 14.1 Workflow Contract 版本化

节点 schema、payload builder、输出结构都需要版本。

原因：

- 模板保存后，未来节点字段变化不能破坏旧模板。
- 工作流运行时应固定 graph_version 和 contract_version。
- 回放历史 run 时，要知道当时使用的节点协议。

建议：

- `node_type` + `contract_version`。
- 模板 fork 时执行 migration。
- 后端保留旧版本 payload builder 的兼容层。

### 14.2 运行快照和可回放

每次运行应保存：

- 输入快照。
- 品牌记忆快照。
- 节点配置快照。
- 模板版本。
- provider/model policy。

这样才能回答：

- 为什么这次生成不一样？
- 用户改了品牌记忆后，旧运行结果是否仍可解释？
- 成本异常来自哪个节点？

### 14.3 权限后移到后端

前端只隐藏按钮不够。

后端必须校验：

- 用户是否属于 organization。
- 用户角色是否能编辑/运行/重试/发布模板。
- Viewer 不能通过直接请求 run endpoint 运行。
- 公开模板发布是否允许当前角色执行。

### 14.4 模板可见性和脱敏

当前模板公开边界需要强化：

- visibility：private、workspace、public。
- public 发布默认关闭。
- public 发布前扫描 brand_context、prompt、reference_links、客户名、密钥格式。
- RAG 和模板搜索默认只查 workspace + 授权 public。

### 14.5 输出大小和资产化策略

不要让 `WorkspaceDraft.nodes.output` 变成无限增长的大 JSON。

建议：

- 节点 output 保存 summary。
- 完整输出进 Asset 或 NodeRun artifact。
- 图片、音频、视频只保存 asset id 和 URL，不内嵌大 payload。
- 长文本输出做截断和详情接口。

### 14.6 测试策略

后端至少补：

- 图编译测试：线性、并行、分支、合流、循环拦截。
- 权限测试：Viewer 不能运行和重试。
- idempotency 测试：重复请求只创建一次 run。
- 节点失败测试：失败策略、跳过、重试、从节点向后跑。
- 模板脱敏测试。
- 成本上限测试。

### 14.7 数据保留和清理

上线测试也需要数据治理：

- 临时运行日志保留周期。
- 大输出 artifact 清理策略。
- 失败任务和取消任务的保留策略。
- public 模板下架和删除策略。
- 用户删除项目后，workflow run、asset、audit 的级联或软删除规则。

## 15. 分阶段执行计划

### Phase W0：后端运行态和性能地基

目标：把工作流从同步草稿执行升级为可追踪、可恢复、可扩展的运行系统。

改动：

- 新增 `WorkflowRun`、`WorkflowNodeRun`、`WorkflowRunEvent`。
- `/drafts/<id>/run/` 改为创建 run 并异步执行。
- 拆分 draft 配置态和 run 运行态。
- 加 idempotency key、run id、node attempt。
- 增加运行详情和节点运行详情 API。
- 工作流列表接口默认只返回摘要。

验收：

- 运行接口快速返回 run id。
- 刷新页面后能恢复 run 状态。
- 节点状态不再依赖完整 draft JSON 反复写入。

### Phase W1：理解门槛和运行前检查

目标：让非技术用户敢点运行。

改动：

- 节点名称业务化。
- 新增节点说明和预计产物。
- 新增运行前检查面板。
- 检查品牌记忆完整度、断开节点、循环、必填配置。
- 阻断项提供修复动作。

验收：

- 无品牌记忆或断开关键节点时不能直接运行。
- 用户能从检查面板跳到具体修复位置。

### Phase W2：运行中可观测

目标：让用户知道工作流运行到哪。

改动：

- 强化节点级状态。
- 节点输出摘要替代 raw JSON，并升级节点卡片可视化。
- 文案类节点卡片显示标题、正文摘要和标签，而不是只显示一段不可读 JSON。
- 图片类节点卡片必须显示缩略图预览；存在 `image_url`、`source_url` 或结果 `url` 时不能只显示链接文本。
- 视频和音频节点显示缩略媒体状态，审阅节点显示风险数量和品牌一致性摘要。
- 长任务提示。
- 刷新后恢复最近运行摘要。
- 工作流运行同步到任务中心。

验收：

- 用户能看到当前节点、已完成节点、失败节点。
- 成功图片节点在画布卡片内可直接看到预览图；预览加载失败时至少保留明确的图片状态和提示词摘要。
- 文案、图片、视频、音频、审阅节点的卡片内容不会挤压标题、状态和连线按钮。
- 长任务不让用户误以为页面卡死。

### Phase W3：失败恢复

目标：失败后不重跑全链路。

改动：

- 失败原因映射为用户文案。
- 支持重试失败节点。
- 支持从某节点向后重跑。
- 支持复制输入快照、节点配置、上游输出和下游影响范围。
- 节点重试加 `Idempotency-Key`，并把 key 写入 `WorkflowRun.idempotency_key`，用于审计和防重复扣费。
- 右侧运行面板和节点右键菜单都提供恢复入口。

验收：

- 单节点失败可以单独恢复。
- 重试不会重复扣费。
- 用户不用看 raw traceback 就能知道失败大类、推荐动作和下一步恢复路径。
- 从任意节点向后重跑时，上游成功产物保留，只重跑目标节点和下游节点。
- 复制诊断信息包含当前节点配置、错误信息、上游输出和下游影响节点。

### Phase W4：产物和资产闭环

目标：工作流不只是运行结果，而是资产生产线。

改动：

- 节点成功产物自动入资产。
- Asset metadata 记录 workflow/node/task 来源。
- Review 节点产物进入审阅流程。
- 运行完成页展示产物清单。
- 资产库 UX 从“所有产物平铺”升级为按来源、工作流 Run、预览可用性组织。
- 资产卡片和预览弹窗直接展示 Run、节点、任务、审阅风险和“仅记录/有源文件”状态。
- 资产 API 支持 `source=workflow`、`workflow_run=<id>`、`workflow_node=<id>`、`has_source=1/0` 过滤。

验收：

- 资产库能按工作流找到产物。
- 审阅风险能回链到节点。
- 用户能快速过滤出工作流产物、手工资产、普通生成资产和缺少源文件的记录。
- 图片、音频、视频如果没有可预览源文件，卡片必须明确提示“仅记录”，不能让用户误以为预览加载失败。

### Phase W5：模板复用和权限安全

目标：让成功 SOP 变成团队资产。

改动：

- 成功运行后一键保存模板。
- 模板增加适用场景、预计产物、所需输入。
- 可见范围：个人 / 工作区 / 公开。
- 公开发布二次确认和脱敏检查。
- Viewer 只读权限收紧。

验收：

- 工作区模板可被同组织成员 fork。
- 公开模板不会泄露私有项目内容。

### Phase W6：分支、判定和合流

目标：让工作流支持真实营销 SOP 中的条件路径。

改动：

- 新增 decision、router、join、human_approval 节点。
- edge 支持条件、默认路径和输出口。
- 后端执行引擎支持 branch trace 和 skipped 节点。
- 前端增加条件边编辑器。
- 运行前检查拦截无默认路径、无效字段、循环。

验收：

- 审阅通过/不通过可以走不同分支。
- 未命中分支不会执行和扣费。
- 运行结果能展示实际路径。

## 16. 不做事项

上线测试前不建议做：

- 完整低代码平台化。
- 任意 JS 脚本节点。
- 复杂分支、循环、条件表达式编辑器。
- 多人实时协同编辑。
- 工作流 marketplace 社交化。

这些能力会显著增加安全和理解成本，当前优先级低于稳定运行、失败恢复和模板复用。

## 17. 完成定义

专项计划完成时应满足：

1. 新用户能从模板创建并运行一条工作流。
2. 运行前问题能被明确指出并修复。
3. 运行中能看到节点级进度。
4. 单节点失败可以恢复。
5. 成功产物能进入资产库。
6. 成功工作流能保存为团队模板。
7. Viewer 不能运行或编辑工作流。
8. 基础指标能支持运营判断卡点。
